# 保险库与操作进度迁移

迁移需要分别处理**程序源码、加密保险库和公开操作进度**。Git 仅传递已提交的源码；浏览器 IndexedDB 中的保险库、网页登录状态及本地进度不会随 `git push`、克隆或拉取自动迁移。

本指南适用于将本版本创建的 HD/PK 保险库恢复到新设备或独立浏览器用户配置。恢复不会合并或覆盖目标中已有的保险库。

## 准备要移交的内容

| 内容 | 用途 | 移交方式 |
| --- | --- | --- |
| 源码、锁文件、文档 | 重新安装同版本程序 | Git 或源码归档 |
| 本地生成的加密备份 JSON | 恢复全部账户及其钱包密钥 | 单独的受控存储或传输 |
| 备份时的原保险库密码 | 解密备份 | 与备份分开保管，操作者自行输入 |
| 公开地址清单及编号 | 核对恢复结果，固定处理对象 | 独立文件，不默认公开发布 |
| 用户名映射、进度文件、分片配置 | 从历史状态继续处理 | 独立文件，经核对后导入计划器 |
| WalletConnect Project ID | 新设备连接中继 | 使用操作者自己的配置 |

不要移交 WalletConnect 连接码、Cookie、登录令牌或浏览器存储导出。官网会话应在目标浏览器重新建立。加密备份虽然没有明文私钥，仍是敏感文件；其清单还包含公开地址和账户名称，不应提交到公共仓库。

## 在来源设备备份

1. 在原浏览器用户配置打开原本使用的本地地址，例如 `http://127.0.0.1:18270/accounts`，自行输入密码解锁。
2. 记录账户数量和每个账户的钱包数量。在 `/connect` 点击“导出编号与地址清单”，保存 `wallet-manifest.json`，并将副本放到 `private-data/wallets.json`。它按页面实际全局顺序导出全部钱包，无需转换地址 TXT；不要排序、去重或重新编号。
3. 返回 `/accounts`，在“备份与恢复验证”输入“当前保险库密码”，点击“下载加密备份”。
4. 等待程序在临时内存保险库中检查完成，保存 JSON 文件。界面提示“备份已生成”只说明生成阶段通过，还需验证保存后的文件。
5. 点击“选择加密备份文件”，重新选择刚保存的文件，输入相同密码，点击“验证备份文件”。
6. 确认全部地址与来源保险库一致，签名验证数量等于钱包总数；如果全部是 HD 钱包，HD 派生核验数量也应等于钱包总数。
7. 保留至少两个独立存储位置的备份，原密码分开保管。迁移验收前继续保留来源保险库。

程序对全部 EVM 钱包签署专用本地验证挑战并校验地址，对 HD 钱包重新派生核对；验证不上传备份或密钥，不发送交易。文件选择上限为 64 MiB，当前格式为 `nado-trading-desk-vault` v1，包含 `wative-core@2.6.0` 原生加密记录。保留对应源码版本和锁文件有利于日后恢复。

HD 账户默认 EVM 派生路径为 `m/44'/60'/0'/0/i`。页面的“钱包编号”从 1 开始，且可能跨多个账户；不要直接把编号当作每个 HD 账户的派生索引。导入私钥的 PK 账户也包含在原生备份中；单组 HD 助记词不能恢复其他 PK 账户。

## 在新设备恢复

1. 安装[README](../README.md)要求的 Node.js 和 Git，检出同一程序版本。Windows 运行 `Setup-Nado.cmd`，或按手动安装步骤使用固定 pnpm 版本完成构建。
2. 启动本地服务，固定使用同一源地址和端口。钱包默认保存在当前浏览器配置的 IndexedDB `nado-ika-custody` 中，不在源码文件夹。
3. 在新的、尚无保险库的正常浏览器用户配置中打开 `/accounts`。不要先点击“创建保险库”。
4. 在“从加密备份恢复”选择备份 JSON，输入备份时的“原保险库密码”，点击“恢复到此浏览器”。
5. 等待内存核验完成后写入目标保险库；处理中保持页面打开。

如果目标已经存在保险库，恢复会停止。保留现有数据，另建空白浏览器配置；不要为了恢复而直接重置或删除旧保险库。错误密码、损坏文件、旧备份和选错保险库应分别核对，不通过改写备份内容绕过验证。

`localhost` 与 `127.0.0.1`、不同协议或不同端口对应不同源。浏览器或用户配置也决定存储隔离。若突然出现“创建保险库”，先确认打开的是原地址及配置，不应直接认定数据已经丢失。

## 验收恢复结果

恢复提示成功后，继续完成以下核对：

1. 账户数、各账户名称和钱包数与来源一致。
2. 在 `/connect` 再次点击“导出编号与地址清单”，将下载文件另存为 `private-data/wallets-restored.json`，保留来源 `wallets.json`。比较两份清单的总数、每个 `walletNumber`、完整 `address` 和顺序，必须全部一致。
3. 在 `/connect` 检查首个、最后一个及即将续接编号的完整地址。编号映射不能因为换设备而重新排列。
4. 在目标保险库的“备份与恢复验证”再次验证迁移文件，确认地址一致及签名检查通过。
5. 刷新页面，重新输入原密码解锁，再次检查数量并导出编号与地址清单，确认数据已经持久保存。

上述流程不要求充值、下单或广播交易。核对失败时保留来源、备份和公开核对结果，先定位问题；不要继续执行下一批操作。来源和目标都能访问同一组钱包时，不要让两个操作者同时处理同一地址。

## 公开地址与进度单独迁移

计划器直接使用 `/connect` 的“导出编号与地址清单”按钮下载的 `wallet-manifest.json`。将它复制为 `private-data/wallets.json` 即可；文件是含 `walletNumber` 和 `address` 的公开 JSON 数组，无需手写或额外解析 TXT。迁移时保留来源清单，确认恢复后的全部编号和地址一致后再用于续接。该清单不能替代加密保险库备份。

进度文件为 NDJSON 或 JSON 数组。成功标准为 `status: "verified_login_and_ink"` 且 `loginComplete: true`，记录应与地址清单相符。保留原始文件；汇总时检查重复编号、同编号不同地址、同地址不同编号和状态冲突。

历史成功表示当时完成过官网流程，**不是新浏览器的有效登录凭证**。新设备需要重新连接官网；日志中的条款确认字段也不能授权新的操作者接受法律声明。

例如，将本地文件放在不提交的 `private-data/` 中：

```powershell
node scripts/registration/cli.mjs status --config registration.config.local.json --wallets private-data/wallets.json --progress private-data/source.ndjson
node scripts/registration/cli.mjs plan --config registration.config.local.json --wallets private-data/wallets.json --progress private-data/source.ndjson --output private-data/resume-plan.json
```

计划器 CLI 会将配置内的路径相对于配置文件目录解析，命令行路径相对于当前工作目录。`--progress` 可重复指定并覆盖配置中的 `progressPaths`；计划器不会悄悄忽略不存在的文件。首次没有历史记录时，显式准备新的空 NDJSON 文件，或使用 `progressPaths: []` 且省略 `--progress`。不要清空已有记录。`--output` 只允许创建新文件，已有输出应换一个文件名，保留原始资料。

默认发布计划为 **10000 → 1 倒序**。历史记录如果按升序完成了一部分，继续时让计划器按新方向跳过已完成编号；不要把“旧日志最大编号 + 1”当作倒序计划的起点。实际少于 10,000 个钱包时，应显式设置边界和起止编号，使计划与清单一致。

实际续接使用 `createPlannedNadoRunner`，把已核对的配置、清单和历史记录传入后，每次 `prepareNext()` 只准备该分片的下一个未完成钱包；`finish` 全部核验且写入进度成功才推进。失败不会跳号，队列为空返回 `null`。默认 `usernamePrefix` 为 `ybtl`，名称由前缀加编号组成；移交时也要保留实际使用的命名规则，不能把已有用户名误当作待覆盖项。

直接调用 CUA 运行器函数时，配置对象已经失去文件目录信息，应先把 `progressPath` 解析为绝对路径，或使用明确写入目标的 `appendProgress` 回调。这与计划器 CLI 的路径解析不同。

## 独立执行器迁移

新设备安装并配置后使用根目录的 `Start-Registration.cmd` 打开专用 Edge 配置，在其本地页面恢复保险库并自行解锁。这个浏览器与日常浏览器、Codex 内置浏览器分别保存数据，不能因为来源浏览器已解锁就跳过恢复。已有专用配置只需解锁，不应反复恢复或重置。

复制 `registration.worker.example.json` 为 `registration.worker.local.json`，核对 `walletsPath`、`progressPaths` 和 `progressPath` 指向单独迁移的公开文件。执行器会新建缺少的输出进度文件；明确指定的其他历史文件缺失时停止。默认 `10000 → 1`，按完整序列固定分片，再跳过已核验项。不能直接复制来源机器的浏览器配置目录、Cookie 或运行锁。

公开清单不存在时，执行器会在解锁后通过 `/connect` 的精确导出按钮下载并验证 JSON，创建 `walletsPath` 后继续同一浏览器的流程；不会覆盖已有来源清单。若只需恢复和核对，可先用 `Open-Registration.cmd`，准备完用 `Stop-Registration.cmd` 关闭后再正式启动。每次启动后自己解锁；首次条款弹窗需阅读并明确确认本次候选摘要。来源进程的确认文件绑定原运行，不能充当新设备或新操作者的同意。

```powershell
node scripts/registration/worker.mjs status --config registration.worker.local.json
node scripts/registration/worker.mjs accept-terms --config registration.worker.local.json --digest <本次候选的SHA256>
```

普通步骤由本地 Playwright 程序直接运行，不需要 AI 或 ChatGPT 浏览器扩展。每小时检查只读取 `status`，不要再启动逐钱包 CUA 任务。异常时保持成功记录，先核对当前项，不能删除操作意图记录来强行重试保存。

本机同一用户全局只允许一个独立执行器或一个并发组，避免多个进程争用系统剪贴板。同机同时使用 Edge 和 Chrome，按 README 的“Edge 和 Chrome 同时执行”配置 `registration.group.local.json`：两个成员必须使用同一地址清单、不同浏览器目录、不同进度输出，以及互不重叠的钱包范围。Chrome 示例从 2500 升序，Edge 示例截止到 2499；旧配置的实际起点及历史路径必须保留，不要直接覆盖。组启动前会校验所有历史，再等待两个浏览器各自恢复并解锁。

迁移并发组时，分别移交两个公开进度文件和必要的历史文件，并在目标设备重新核对本次条款；不要复制源设备的锁、同意文件、浏览器目录或临时保存意图来冒充新的核验结果。若源设备尚有未完成保存，先在源设备处理确认结果，再迁移。单独从 Edge 换为 Chrome 时，必须同步更改 `browser` 与 `profileName`。跨设备分片仍需明确固定范围；完整一万钱包或多设备官网并行未作为已实测结果。

## 旧 CUA 方式：Edge、Chrome 与分片

本节只针对旧 `cua-runner.mjs`。该官网辅助流程只实测 IAB；尚未验证 Edge/Chrome 外部浏览器并行。源码包含计划分片不代表外部浏览器已经能够自动并发执行。

使用外部浏览器前，按[官方扩展说明](https://learn.chatgpt.com/docs/chrome-extension)在应用“设置 → Computer Use”选择浏览器，点击 **Install** 安装官方扩展，确认变为 **Manage**。在安装扩展的浏览器用户配置中通过 `@Edge` 或 `@Chrome` 连接，保持操作者自行设置的网站权限。

每条并行通道需要：

- 独立浏览器用户配置，而非同配置里的普通新窗口。
- 在该配置中独立恢复并解锁保险库，逐一核对编号和地址；扩展不会自动迁移或解锁保险库。
- 相同范围、方向、公开地址清单和分片总数，以及互不相同的 `laneIndex`。
- 独立进度文件，并明确当前负责的通道，避免重复处理。

分片基于完整遍历序列的固定位置取模，先分片再跳过完成项。例如倒序两通道：`laneIndex: 0` 处理 `10000、9998…`，`laneIndex: 1` 处理 `9999、9997…`。不能各自删除完成项后重新分片；调整 `laneCount` 前应停止全部通道，合并进度再重新生成计划。

先完成两个独立配置的小规模验证，再评估实际并行能力。遇到条款变化、验证码、来源验证失败、权限拒绝或未预期的签名请求时，停止当前项，由操作者决定下一步。文档和示例不预先授权接受条款，也不提供绕过网站限制的方式。

`createPlannedNadoRunner` 对 `browser: "chrome"` 或 `"edge"` 要求显式指定 `smokeTestWalletNumber`，且必须是当前分片的首个未完成编号。首钱包的官网地址、用户名、Ink 网络、本地签署结果和进度写入全部成功后，才放行其他编号；重新创建运行器需重新通过此检查。`prepareNext` 返回当前条款，`finish` 需要本次明确确认的六项声明、上下文及官方链接。旧日志中的条款字段不能替代这个确认。

同机多个浏览器配置仍可能共用系统剪贴板。并行通道必须在同一 CUA 会话中复用同一个运行器模块实例，使用模块共享锁串行完成连接码复制、读取、填入及清空。两个不共享锁的执行器不得并发执行 **Copy link**；不同会话不能仅凭分片不重复就视为配对安全。

## 发布前的文件边界

仓库只发布代码、无个人数据的配置示例及文档。以下内容单独保管并排除提交：

- `nado-vault-*.json` 等保险库备份，助记词、私钥、密码和恢复密钥。
- `.env` 类配置、本地 `registration.config.local.json`、个人项目配置。
- `private-data/` 中的地址、用户名映射、队列计划和进度。
- `.local/`、`test-results/`、浏览器配置、截图、日志、Cookie 和令牌。

`.gitignore` 不会移除已经跟踪或进入历史的文件。移交前检查待提交内容和历史；不要为图方便使用强制添加，把私人文件放进公开 Git。若只是迁移源码，目标设备看到空保险库是正常情况，继续按本指南恢复即可。
